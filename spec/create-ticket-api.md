# Task REST API Foundation and Create Ticket

## Objective

Expose the first REST API for the Support Ticket Management System.

Implement the REST API foundation and the Create Ticket endpoint while following the approved API contract and backend business rules.

## Endpoint

Implement:

```text
POST /api/v1/tickets
```

## Request

The request must contain only fields permitted by the approved API contract.

Expected business fields:

* title
* description
* priority
* assignee

The client must not control:

* id
* status
* created_at
* updated_at

## Creation Rules

When a ticket is created:

* status must be `OPEN`
* ID is generated by the backend
* created timestamp is backend controlled
* updated timestamp is backend controlled
* priority must be valid
* required fields must be validated

The controller must not implement business rules.

The existing ticket service must remain responsible for business behavior.

## DTOs

Do not expose JPA entities directly from the REST API.

Use dedicated request/response DTOs.

Request DTO:

```text
CreateTicketRequest
```

Response DTO:

```text
TicketResponse
```

The response must contain the appropriate ticket information according to `spec/api-contract.md`.

## Validation

Backend validation is mandatory.

At minimum validate the requirements defined by the approved specification for:

* title
* description
* priority
* assignee where applicable

Invalid requests must receive a controlled client-error response.

Do not return stack traces or internal exceptions.

## HTTP Status

Successful ticket creation must return the status code defined by `spec/api-contract.md`.

If the specification does not explicitly define it, use:

```text
201 Created
```

## Error Handling

Use the project's centralized exception-handling mechanism.

Validation errors must be represented consistently.

Business exceptions must not expose internal implementation details.

The error response should provide a meaningful message that can later be consumed by the frontend.

## API Versioning

Use:

```text
/api/v1
```

Do not introduce multiple API versions.

## Controller Responsibilities

The controller should:

1. Receive HTTP request.
2. Validate request DTO.
3. Call the ticket service.
4. Map the result to the response DTO.
5. Return the appropriate HTTP response.

The controller must not:

* implement state-machine logic
* access repositories directly
* contain database logic
* implement ticket business rules

## Testing

Add:

### Controller tests

Verify:

* valid ticket creation
* invalid title
* invalid description
* invalid priority
* required field validation
* correct HTTP status
* response structure

### Service integration

Verify:

* created ticket starts with OPEN
* ID is generated
* ticket is persisted

Use the existing PostgreSQL-compatible test strategy.

Do not use H2.

## API Documentation

Document the endpoint according to the project's documentation standards.

If OpenAPI/Swagger is already approved in the architecture, use it consistently.

Do not add unnecessary documentation dependencies.

## Out of Scope

Do not implement:

* list tickets
* ticket details
* update ticket
* comments
* search
* filtering
* status transition endpoint
* frontend
* authentication
* authorization

## Completion Criteria

The task is complete when:

* `POST /api/v1/tickets` exists.
* Valid requests create tickets.
* New tickets always start as `OPEN`.
* Client cannot control status.
* Backend validation works.
* Invalid requests return meaningful errors.
* JPA entities are not exposed directly.
* Controller remains thin.
* Tests pass.
* API follows the approved contract.
* AI review is completed.
* Human review is completed.
