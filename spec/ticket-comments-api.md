# Ticket Comments API

## Objective

Implement the REST API for adding comments to an existing support ticket.

Endpoint:

`POST /api/v1/tickets/{ticketId}/comments`

A comment belongs to exactly one ticket.

## Scope

This step implements:

* comment creation
* comment persistence
* comment validation
* ticket existence validation
* REST endpoint
* response DTO
* service-layer business logic
* tests

## Request

```json
{
  "content": "I have investigated the issue.",
  "author": "rajdeep"
}
```

### Fields

#### content

Required.

Rules:

* must not be null
* must not be blank
* must contain meaningful content

#### author

Required.

Rules:

* must not be null
* must not be blank

No authentication or user-management system is required for this assignment.

The author is represented as a string.

## Ticket Existence

The ticket ID is supplied through the URL:

```text
/api/v1/tickets/{ticketId}/comments
```

If the ticket does not exist:

```text
HTTP 404 Not Found
```

No comment should be created.

## Successful Creation

On successful creation:

```text
HTTP 201 Created
```

Return the created comment using a dedicated response DTO.

Do not expose the JPA entity directly.

Example:

```json
{
  "id": 10,
  "ticketId": 1,
  "content": "I have investigated the issue.",
  "author": "rajdeep",
  "createdAt": "2026-09-25T11:30:00Z"
}
```

## Persistence

Persist the comment using the existing PostgreSQL database.

The relationship must use the existing ticket as the parent.

The database relationship should enforce:

```text
comment.ticket_id → ticket.id
```

Comments must not exist without a valid ticket.

## Business Logic

The controller must remain thin.

The service/application layer should:

1. Validate that the ticket exists.
2. Validate the comment data.
3. Create the comment.
4. Associate the comment with the ticket.
5. Persist the comment.
6. Return the created comment.

Do not place business logic inside the controller.

## Timestamp

`createdAt` must be generated by the backend.

The client must not be allowed to supply or override:

* id
* createdAt
* ticketId

These values are controlled by the backend/application.

## Error Handling

Use the existing centralized error handling.

Expected status codes:

* `201` — comment created
* `400` — validation error
* `404` — ticket not found
* `500` — unexpected server error

## Validation

The backend is authoritative.

The following should return HTTP 400:

```json
{
  "content": ""
}
```

```json
{
  "content": "Some comment",
  "author": ""
}
```

Also reject:

```json
{
  "content": null,
  "author": "rajdeep"
}
```

and:

```json
{
  "content": "Some comment",
  "author": null
}
```

## Architecture

Follow the existing architecture:

```text
Controller
    ↓
Service/Application Layer
    ↓
Repository
    ↓
PostgreSQL
```

Use DTOs at the API boundary.

Do not expose JPA entities.

The repository should focus on persistence rather than business rules.

## Tests

Add tests covering:

### Successful creation

1. Create comment for existing ticket.
2. Return HTTP 201.
3. Response contains generated comment ID.
4. Response contains correct ticket ID.
5. Response contains content.
6. Response contains author.
7. Response contains generated createdAt.

### Validation

8. Missing content → 400.
9. Blank content → 400.
10. Missing author → 400.
11. Blank author → 400.
12. Null content → 400.
13. Null author → 400.

### Ticket relationship

14. Missing ticket → 404.
15. Missing ticket does not create a comment.
16. Created comment references the correct ticket.

### Persistence

17. Comment remains persisted after request completion.
18. Comment is retrievable through the ticket detail API if the existing detail implementation already supports comments.

### API boundary

19. Client cannot control comment ID.
20. Client cannot control createdAt.
21. Client cannot change ticketId through the request body.

## Existing Ticket Detail API

The existing:

```http
GET /api/v1/tickets/{ticketId}
```

should include comments according to the approved API contract.

If the current Step 15 implementation does not yet include comments because comments did not exist at that time, update the detail response only as required to expose persisted comments.

Do not implement a separate comment retrieval endpoint in this step.

## Out of Scope

Do not implement:

* comment update
* comment deletion
* standalone comment retrieval endpoint
* search
* filtering
* pagination
* sorting
* frontend UI
* authentication
* authorization
* notifications
* Kafka
* RabbitMQ
* Elasticsearch
* Redis
* microservices

## Definition of Done

* Comment entity/model is correctly mapped.
* Comment repository exists.
* Comment service exists.
* Comment creation endpoint works.
* Ticket existence is validated.
* Backend validation works.
* Comment is persisted in PostgreSQL.
* Response DTO is used.
* HTTP 201 is returned for successful creation.
* HTTP 404 is returned for missing tickets.
* HTTP 400 is returned for invalid requests.
* Centralized error handling is reused.
* Tests pass.
* Existing ticket functionality remains working.
* No H2 database is introduced.
* No unrelated functionality is changed.
