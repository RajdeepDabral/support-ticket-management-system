# Ticket Details + Edit Ticket UI

## Objective

Implement the ticket details page and the ability to update editable ticket fields.

The user must be able to:

* Open a ticket from the ticket list.
* View ticket details.
* Edit title.
* Edit description.
* Edit priority.
* Change assignee.
* Save changes.
* Receive meaningful validation and error messages.

The ticket status must not be changed through the normal edit form.

Status changes will be handled separately through the backend state-machine workflow.

---

## Route

Implement:

```text
/tickets/:ticketId
```

The existing ticket list navigation from Step 22 must point to this route.

---

## Load Ticket

When the details page opens, retrieve the ticket using the existing backend API contract.

Expected endpoint:

```http
GET /api/v1/tickets/{ticketId}
```

Do not create a duplicate endpoint.

---

## Ticket Details

Display at minimum:

* Ticket ID
* Title
* Description
* Priority
* Status
* Assignee
* Created timestamp
* Updated timestamp

The status must be displayed as read-only.

---

## Loading State

While retrieving ticket details, display a meaningful loading state.

Do not show an empty ticket form while the request is still loading.

---

## Not Found

If the backend returns HTTP 404:

Display a meaningful message such as:

```text
Ticket not found.
```

Provide a way to return to the ticket list.

Do not display raw backend exception information.

---

## General Load Error

If ticket retrieval fails unexpectedly:

Display a meaningful error such as:

```text
Unable to load ticket.
Please try again.
```

Provide a retry option where practical.

---

# Edit Mode

The ticket details page should provide an Edit action.

Example:

```text
[ Edit Ticket ]
```

When editing begins, the following fields become editable:

* Title
* Description
* Priority
* Assignee

The following fields must remain read-only:

* Ticket ID
* Status
* Created timestamp
* Updated timestamp

---

## Editable Fields

### Title

Required.

Cannot be blank.

### Description

Required.

Cannot be blank.

### Priority

Must use the existing supported priority values.

Do not invent new values.

### Assignee

Required according to the existing API contract.

---

## Update API

Use the existing backend update endpoint.

The exact HTTP method and payload must come from the approved API contract and actual backend implementation.

Do not invent an endpoint.

For example, if the existing contract specifies:

```http
PUT /api/v1/tickets/{ticketId}
```

then use that contract.

If it specifies another method, use the approved method.

---

## Update Payload

Only editable fields should be submitted.

The frontend must not attempt to modify:

* id
* status
* createdAt
* updatedAt

The status state machine must remain controlled by the backend.

---

## Validation

Client-side validation should provide immediate feedback for:

* blank title
* blank description
* invalid/missing priority
* blank assignee where required

Backend validation remains authoritative.

If backend validation fails, display meaningful feedback.

Do not expose raw stack traces or raw exception objects.

---

## Save

When Save is clicked:

1. Validate the form.
2. Prevent duplicate submissions.
3. Display a saving state.
4. Send the update request.
5. Process the backend response.
6. Display the updated ticket.

The Save button must be disabled while the request is in progress.

---

## Cancel Editing

When editing is cancelled:

* Do not send an API request.
* Restore the previously loaded ticket values.
* Return to read-only mode.

Do not silently persist unsaved changes.

---

## Successful Update

After successful update:

* Exit edit mode.
* Display the updated values.
* Preserve the ticket route.
* Provide meaningful success feedback if consistent with the existing UI.

Do not unnecessarily navigate away from the ticket.

---

## Error Handling

Handle:

### HTTP 400

Display backend validation errors.

### HTTP 404

Display that the ticket no longer exists.

### HTTP 500

Display:

```text
Unable to update ticket.
Please try again.
```

### Network failure

Display a meaningful network/API error.

The user should be able to retry.

---

# Status Protection

The normal edit form must never send a status value.

For example, this must not be generated by the frontend:

```json
{
  "title": "...",
  "description": "...",
  "priority": "HIGH",
  "assignee": "...",
  "status": "CLOSED"
}
```

Status changes belong to the dedicated state-machine functionality.

---

# Navigation

The details page must provide a way to return to:

```text
/tickets
```

The existing ticket list should continue to navigate to:

```text
/tickets/:ticketId
```

---

# API Layer

Reuse the existing ticket API abstraction.

Expected conceptual methods may include:

```text
getTicket(ticketId)
updateTicket(ticketId, request)
```

Do not place raw HTTP implementation throughout React components.

---

# TypeScript

Use explicit types.

Do not use:

```typescript
any
```

for ticket data or update requests.

Create/reuse appropriate types such as:

```text
Ticket
UpdateTicketRequest
```

based on the actual backend contract.
