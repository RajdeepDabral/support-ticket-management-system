# Task Ticket Domain and Business Service

## Objective

Implement the core ticket business layer on top of the persistence layer created in Task 11.

The business layer must provide controlled operations for creating, retrieving, and updating tickets while keeping business rules outside REST controllers and repositories.

## Scope

Implement:

* Ticket service/application layer
* Ticket creation logic
* Ticket retrieval logic
* Ticket update logic
* Ticket existence/not-found handling
* Request/domain validation where appropriate
* Mapping between persistence objects and domain/service representations where required
* Unit tests for business behavior

## Ticket Creation

When a ticket is created:

* title is required
* description is required according to the approved specification
* priority is required and must be valid
* assignee may be provided according to the approved specification
* status must always start as OPEN
* ID must be generated by the backend
* created timestamp must be backend controlled
* updated timestamp must be backend controlled

The caller must not be able to choose the initial status.

## Ticket Retrieval

The service must support retrieval of an existing ticket.

If the ticket does not exist, the service must produce the project's defined not-found error.

Do not return null for a missing ticket.

## Ticket Update

The service must allow updating only the fields permitted by the approved API contract:

* title
* description
* priority
* assignee

The general update operation must not directly modify status.

Status changes will be handled separately by the state-machine operation.

## Business Rules

Business rules belong in the service/domain layer rather than:

* REST controllers
* repositories
* frontend code

The frontend must never be treated as the source of truth for business rules.

## Validation

Backend validation remains authoritative.

Do not rely exclusively on frontend validation.

Avoid duplicating validation rules unnecessarily across layers.

## Error Handling

Use the project's centralized error-handling approach.

The service must distinguish between:

* resource not found
* invalid request
* invalid business operation

Do not expose database or implementation exceptions directly.

## Transactions

Use appropriate service-level transaction boundaries.

Do not add transactions indiscriminately to every method.

Ticket creation and update operations should behave atomically.

## State Machine

Do not implement the complete status transition mechanism in this task.

Do not allow status modification through create/update service methods.

The dedicated state-machine task will implement:

OPEN → IN_PROGRESS
OPEN → CANCELLED
IN_PROGRESS → RESOLVED
IN_PROGRESS → CANCELLED
RESOLVED → CLOSED

## Testing

Add unit tests covering:

### Creation

* valid ticket creation
* initial status is OPEN
* backend-generated ID
* required fields
* priority handling

### Retrieval

* existing ticket
* unknown ticket

### Update

* title update
* description update
* priority update
* assignee update
* status cannot be changed through normal update

## Out of Scope

Do not implement:

* REST controllers
* REST endpoints
* status transition implementation
* comments
* search
* filtering
* frontend
* authentication
* authorization
* pagination
* Kafka
* Redis
* Elasticsearch

## Completion Criteria

The task is complete when:

* Ticket service/application layer exists.
* Ticket creation is implemented.
* Ticket retrieval is implemented.
* Ticket update is implemented.
* Status is protected from normal updates.
* Not-found behavior is implemented.
* Unit tests pass.
* Business logic is not placed in controllers or repositories.
* No unrelated functionality is introduced.
* AI review is completed.
* Human review is completed.
