# Support Ticket Management System

## Data Model Specification

**Document:** Data Model Specification
**Version:** 1.0
**Status:** Approved for Implementation
**Database:** PostgreSQL
**ORM/Persistence:** JPA / Hibernate
**Backend:** Java 21 + Spring Boot

---

# 1. Purpose

This document defines the relational data model for the Support Ticket Management System.

The model supports the requirements defined in:

```text
spec/requirements.md
```

and follows the architecture defined in:

```text
spec/architecture.md
```

The database is responsible for persistent storage of tickets and comments.

Business rules such as ticket state transitions remain application-level responsibilities and must not be delegated solely to database constraints.

---

# 2. Data Model Overview

The initial database contains two primary entities:

```text
Ticket
  |
  | 1 : N
  |
  └────────── Comment
```

A ticket can have zero or more comments.

Each comment belongs to exactly one ticket.

---

# 3. Entity: Ticket

The `ticket` table represents a support ticket.

## Logical Attributes

| Attribute   | Description                               |
| ----------- | ----------------------------------------- |
| id          | Unique identifier for the ticket          |
| title       | Ticket title                              |
| description | Detailed ticket description               |
| priority    | Ticket priority                           |
| status      | Current ticket lifecycle status           |
| assignee    | Current ticket assignee                   |
| created_at  | Time at which the ticket was created      |
| updated_at  | Time at which the ticket was last updated |

---

# 4. Ticket Table

The logical PostgreSQL structure is:

| Column      | PostgreSQL Type          | Nullable | Constraint                     |
| ----------- | ------------------------ | -------: | ------------------------------ |
| id          | BIGINT                   |       No | Primary Key                    |
| title       | VARCHAR(255)             |       No | Not blank at application level |
| description | TEXT                     |       No | Not blank at application level |
| priority    | VARCHAR(30)              |       No | Valid priority                 |
| status      | VARCHAR(30)              |       No | Valid status                   |
| assignee    | VARCHAR(255)             |       No | Required                       |
| created_at  | TIMESTAMP WITH TIME ZONE |       No | Creation timestamp             |
| updated_at  | TIMESTAMP WITH TIME ZONE |       No | Last update timestamp          |

The exact identifier-generation mechanism will be finalized during implementation.

---

# 5. Ticket Identifier

Each ticket shall have a unique identifier.

The identifier should be generated by the backend/database rather than supplied by the client.

The client must not be able to arbitrarily choose the identifier of a newly created ticket.

The initial implementation may use a PostgreSQL-compatible generated numeric identifier.

---

# 6. Ticket Title

The ticket title shall be stored as:

```text
VARCHAR(255)
```

The backend shall reject blank titles.

The exact minimum/maximum validation rules will be aligned with the API validation specification.

The database column length is intended to prevent unexpectedly large title values.

---

# 7. Ticket Description

The ticket description shall be stored as:

```text
TEXT
```

The backend shall reject blank descriptions.

A `TEXT` column is used because descriptions may be substantially larger than a normal short string field.

---

# 8. Ticket Priority

The ticket priority shall represent the priority associated with a support ticket.

The application shall define a controlled set of priority values.

The exact allowed values will be defined in the API contract and Java domain model.

The database representation will use:

```text
VARCHAR(30)
```

rather than a PostgreSQL-specific enum type.

### Reason

Using a string representation keeps the database schema less tightly coupled to PostgreSQL-specific enum definitions and makes future application-level changes easier to manage.

The application remains responsible for validating that the supplied value is one of the supported priorities.

---

# 9. Ticket Status

The ticket status represents the current lifecycle state.

Supported statuses are:

```text
OPEN
IN_PROGRESS
RESOLVED
CLOSED
CANCELLED
```

The database representation will use:

```text
VARCHAR(30)
```

The application will map these values to a Java enum.

Conceptually:

```text
Java
TicketStatus.OPEN
TicketStatus.IN_PROGRESS
TicketStatus.RESOLVED
TicketStatus.CLOSED
TicketStatus.CANCELLED

        ↓

PostgreSQL

"OPEN"
"IN_PROGRESS"
"RESOLVED"
"CLOSED"
"CANCELLED"
```

---

# 10. Status Transition Responsibility

The database stores the current status.

The application owns the transition rules.

The database must not be treated as the primary state-machine implementation.

For example:

```text
CLOSED → OPEN
```

must be rejected by the backend before the new status is persisted.

This rule will be defined in detail in:

```text
spec/state-machine.md
```

---

# 11. Ticket Assignee

The assignment requires that a ticket have an assignee and that the assignee can be changed.

The initial data model will represent the assignee as:

```text
VARCHAR(255)
```

A separate `user` table is intentionally not introduced.

### Reason

The assignment does not require:

* user registration
* authentication
* authorization
* user administration
* teams
* roles

Creating those entities would introduce additional complexity outside the stated requirements.

If user management becomes a future requirement, the assignee model can be evolved later.

---

# 12. Ticket Timestamps

Two timestamps are required:

```text
created_at
updated_at
```

### created_at

Records when the ticket was created.

It should not be modified during normal ticket updates.

### updated_at

Records when the ticket was last modified.

It should be updated when relevant ticket information changes.

The implementation should use a consistent timezone strategy.

PostgreSQL will use:

```text
TIMESTAMP WITH TIME ZONE
```

for persisted timestamps.

The application should use Java's modern date/time API rather than legacy date classes.

---

# 13. Entity: Comment

The `comment` table represents a comment associated with a ticket.

## Logical Attributes

| Attribute  | Description                         |
| ---------- | ----------------------------------- |
| id         | Unique comment identifier           |
| ticket_id  | Ticket to which the comment belongs |
| content    | Comment text                        |
| author     | Comment author                      |
| created_at | Comment creation timestamp          |

---

# 14. Comment Table

The logical PostgreSQL structure is:

| Column     | PostgreSQL Type          | Nullable | Constraint                     |
| ---------- | ------------------------ | -------: | ------------------------------ |
| id         | BIGINT                   |       No | Primary Key                    |
| ticket_id  | BIGINT                   |       No | Foreign Key                    |
| content    | TEXT                     |       No | Not blank at application level |
| author     | VARCHAR(255)             |       No | Required                       |
| created_at | TIMESTAMP WITH TIME ZONE |       No | Creation timestamp             |

---

# 15. Ticket–Comment Relationship

The relationship is:

```text
Ticket
  |
  | 1
  |
  | N
  ▼
Comment
```

A ticket can contain:

```text
0..N comments
```

Each comment belongs to:

```text
exactly 1 ticket
```

The database shall enforce this relationship using a foreign key.

Conceptually:

```text
comment.ticket_id
        ↓
ticket.id
```

---

# 16. Referential Integrity

A comment must not exist without a corresponding ticket.

Therefore:

```text
comment.ticket_id → ticket.id
```

will be represented as a foreign-key relationship.

The application should not create orphan comments.

---

# 17. Ticket Deletion

Ticket deletion is not part of the stated assignment requirements.

Therefore, no delete-ticket API is required.

The initial application will not introduce ticket deletion functionality simply because a database `DELETE` operation is technically possible.

This avoids adding behavior that is not part of the requested scope.

The behavior of existing comments if ticket deletion is introduced in a future version will be decided as part of that future requirement.

---

# 18. Database Constraints

The database should provide appropriate structural constraints.

At minimum:

### Ticket

```text
PRIMARY KEY (id)

NOT NULL:
title
description
priority
status
assignee
created_at
updated_at
```

### Comment

```text
PRIMARY KEY (id)

NOT NULL:
ticket_id
content
author
created_at

FOREIGN KEY:
ticket_id → ticket.id
```

Application validation remains responsible for semantic rules such as:

```text
title must not be blank
description must not be blank
priority must be valid
status must be valid
comment content must not be blank
```

---

# 19. Indexing Strategy

Indexes will be introduced based on actual query requirements.

The initial expected query patterns are:

1. Find ticket by ID.
2. List tickets.
3. Filter tickets by status.
4. Search tickets by title/description.
5. Retrieve comments for a ticket.

The primary key automatically provides an index for:

```text
ticket.id
comment.id
```

A database index should be considered for:

```text
ticket.status
comment.ticket_id
```

because these correspond directly to expected filtering and relationship queries.

---

# 20. Search Strategy

The requirement states that tickets must be searchable by keyword.

The initial search scope is:

```text
ticket.title
OR
ticket.description
```

The initial implementation does not require Elasticsearch or another external search engine.

A PostgreSQL-based implementation is sufficient for the scope of this assignment.

Search behavior and API semantics will be defined in:

```text
spec/api-contract.md
```

The exact PostgreSQL query strategy will be finalized during implementation.

---

# 21. Data Ownership

The application owns the following data:

```text
Ticket
Comment
```

The frontend does not own persistent ticket state.

The backend is responsible for persistence.

PostgreSQL is the persistent source of stored application data.

---

# 22. Persistence Lifecycle

The expected lifecycle is:

```text
Frontend
   ↓
REST API
   ↓
Service
   ↓
Repository
   ↓
PostgreSQL
```

For retrieval:

```text
PostgreSQL
   ↓
Repository
   ↓
Service
   ↓
REST API
   ↓
Frontend
```

The application must not rely on an in-memory collection as the primary data store.

---

# 23. Transaction Boundaries

Operations that modify persistent data should execute within appropriate transaction boundaries.

Examples include:

```text
Create Ticket
Update Ticket
Change Ticket Status
Add Comment
```

The transaction boundary should generally be located at the service/application layer.

Controllers should not manage database transactions directly.

---

# 24. Concurrent Updates

Ticket updates may theoretically be made by multiple clients.

The implementation should consider protection against lost updates where appropriate.

A simple optimistic locking approach may be considered if it can be implemented without unnecessary complexity.

This decision will be made during implementation based on the actual update model.

No distributed locking mechanism is required by the assignment.

---

# 25. Database Migration

Database schema changes should be version-controlled.

The project should use a database migration mechanism rather than relying on undocumented manual database changes.

The specific migration tool will be selected during implementation.

The migration history should be committed to Git so that a clean environment can recreate the database schema.

---

# 26. Docker Database

PostgreSQL will run as a Docker Compose service for the standard local/reviewer environment.

The database configuration should support:

* database name
* username
* password
* port
* persistent volume

The Docker setup should ensure that application restart does not unintentionally delete persisted database data.

---

# 27. Persistence Across Application Restart

The requirement states that data must survive application restart.

The Docker environment should therefore separate:

```text
Application container lifecycle
```

from:

```text
PostgreSQL data lifecycle
```

A PostgreSQL Docker volume will be used so that restarting/recreating the application container does not remove database data.

The exact volume configuration will be documented in the Docker setup.

---

# 28. JPA/Hibernate Considerations

The implementation should avoid exposing JPA-specific behavior through the REST API.

JPA entities represent persistence concerns.

API DTOs represent external API concerns.

The application should avoid:

* Returning entities directly from controllers.
* Relying on lazy-loading behavior during JSON serialization.
* Embedding business rules only in entity setters.
* Performing uncontrolled database access from serialization.

---

# 29. Database Naming Convention

Database objects should follow a consistent naming convention.

The preferred convention is:

```text
snake_case
```

Examples:

```text
ticket
comment
ticket_id
created_at
updated_at
```

Java properties may follow standard Java naming conventions:

```text
ticketId
createdAt
updatedAt
```

The mapping between Java and PostgreSQL naming should be explicit where necessary.

# 31. Data Model Decisions

## Decision 1 — Two primary tables

The initial model contains:

```text
ticket
comment
```

No additional entities are required by the assignment.

---

## Decision 2 — PostgreSQL

PostgreSQL is the application's persistent database.

No in-memory database is used as the application's runtime database.

---

## Decision 3 — String representation for statuses

The PostgreSQL column stores status as a string while Java uses an enum.

Reason:

This keeps the domain model strongly typed while avoiding unnecessary database-specific enum coupling.

---

## Decision 4 — String representation for priority

Priority is stored as a string and validated at the application layer.

Reason:

This keeps the schema straightforward and allows the supported priority set to be controlled by the application contract.

---

## Decision 5 — Assignee without User entity

The assignee is stored as an application-level value.

Reason:

The assignment requires assignment functionality but does not require authentication or user management.

---

## Decision 6 — No ticket deletion

Ticket deletion is not introduced because it is not part of the assignment requirements.

---

## Decision 7 — No Elasticsearch

Search will initially use PostgreSQL.

Reason:

The assignment requires keyword search but does not require a dedicated search engine.

Introducing Elasticsearch would add infrastructure and complexity without being necessary for the stated functionality.
